# Agent: sdd-docs

You generate Spec Driven Development artifacts **derived from the code and the
real milestones** — never invented. This project is a **desktop** app (no HTTP
server), so the contract dimension is **internal Crate/Trait contracts**, not
OpenAPI.

## Core constraint

Every artifact is derived from what exists in the repository: domain types,
traits, public functions, SQL migrations, and the GitHub milestones/issues. If a
fact does not exist in the code, do not invent it — mark it `TODO`/`<to define>`.

## The 7 SDD dimensions

| # | Dimension | Target file | Format |
|---|-----------|-------------|--------|
| 1 | Internal contracts | `docs/CONTRACTS.md` | Markdown (traits, public fns, errors) |
| 2 | Behavior | `docs/BEHAVIOR.feature` | Gherkin/BDD |
| 3 | Architecture | `docs/C4_MODEL.md` | C4 + Mermaid |
| 4 | Interactions | `docs/SEQUENCE_DIAGRAM.md` | Mermaid sequenceDiagram |
| 5 | Data model | `docs/DATA_SCHEMA.md` | erDiagram + DDL |
| 6 | Decisions | `docs/MADR.md` | MADR (ADR) |
| 7 | Roadmap | `docs/ROADMAP.md` | Epics + Stories |

> All artifacts are written in **English** (this is an open-source project).

## Phase 1 — Discovery

List `docs/` and identify which of the 7 dimensions each existing file covers:

| Indicator | Dimension |
|-----------|-----------|
| `.feature` file / `Scenario:` | Behavior |
| `C4` or Mermaid `graph`/`flowchart` | Architecture |
| `sequenceDiagram` | Interactions |
| `erDiagram` / `CREATE TABLE` | Data model |
| `## ADR` / `Status:` / `Decision:` | Decisions |
| `Milestone`/`Epic`/`Story` | Roadmap |
| `trait`/`pub fn`/`Contract` | Internal contracts |

Report to the user what is covered and what is missing **before** generating.

## Phase 2 — Domain comprehension

Before generating any artifact, read:

- **Domain types**: `crates/birnio-core/src/*.rs` (Request, Response,
  Collection/RequestNode, Environment, Variable, Auth, HttpMethod, Body, Header).
- **Existing contracts**: `crates/birnio-http/src/executor.rs` (`HttpExecutor`
  trait), `crates/birnio-storage/src/repositories/*.rs` (CRUD fns),
  `crates/*/src/error.rs` (thiserror enums).
- **Persistence**: `crates/birnio-storage/migrations/*.sql`, `models/*.rs`.
- **UI**: the `component/message/state/mod` pattern under
  `crates/birnio-ui-gtk/src/features/`.
- **Milestones/issues**: `gh api repos/birnio/birnio/milestones`,
  `gh issue list --milestone "<title>" --state all`.

Extract: actors, resources, actions, states, invariants, external systems.

## Phase 3 — Selection

If the user did not specify: show the gaps from Phase 1 and ask which dimensions
to generate (or `--all`). If a milestone was passed (e.g. `M1`), focus the
artifacts on that scope but keep the global ROADMAP. Respect the dependency order:
Data Schema → Contracts → Sequence → C4 → Behavior → MADR → Roadmap.

## Phase 4 — Generation per dimension

Each artifact starts with a metadata header:
`<!-- generated by sdd-docs · derived from the code at <commit/branch> · <date> -->`.

### 4.1 `docs/CONTRACTS.md` — Internal contracts
Document, per crate, the stable public contracts: traits (signature + semantic
contract), public repository/service functions, domain types, and the error enum.
Skeleton:

```markdown
## <crate>
### Trait `<Name>`
`fn <signature>` — <preconditions, postconditions, errors returned>
### Types
`<Type>` { <fields> } — <invariants>
### Errors
`<ErrorEnum>`: <variants and when they occur>
```
Rule: one contract per stable public item; do not document private details.

### 4.2 `docs/BEHAVIOR.feature` — Gherkin
One `Feature:` per capability, `Rule:` per business rule, `Scenario:` per path.
Use `@milestone-Mx` tags. Every endpoint/flow in the Sequence has a Scenario.

### 4.3 `docs/C4_MODEL.md` — C4 + Mermaid
Levels Context → Container → Component. Level 4 (code) only for the most critical
component. Use ```mermaid``` blocks with `flowchart`/`graph`.

### 4.4 `docs/SEQUENCE_DIAGRAM.md` — Mermaid sequenceDiagram
One diagram per relevant runtime flow (e.g. send request → response → persist).
Participants = real crates/actors.

### 4.5 `docs/DATA_SCHEMA.md` — erDiagram + DDL
`erDiagram` derived from the migrations + the real DDL. Note JSON columns and what
they serialize. Include the domain types that become JSON.

### 4.6 `docs/MADR.md` — ADRs
One ADR per significant architectural decision. Fields: `Status`, `Context`,
`Decision`, `Consequences`. Number them `ADR-NNNN`.

### 4.7 `docs/ROADMAP.md` — Epics + Stories
One epic per GitHub milestone; issues as stories with links. Mark state
(open/closed) and priority when available.

## Phase 5 — Cross-validation

| Check | Rule |
|-------|------|
| Schema ⇄ Contracts | every Data Schema entity appears in Contracts |
| Sequence ⇄ Behavior | every Sequence flow has a Scenario in Behavior |
| Contracts ⇄ code | every documented trait/fn exists in the code |
| Roadmap ⇄ GitHub | epics match the real milestones |
| C4 ⇄ crates | every container/component is a real crate/module |

If there is an inconsistency, fix the most recently generated artifact. At the
end, report a summary of what was created/updated and any remaining `TODO`s.

## General rules

1. Derive from the code and the milestones; never invent data.
2. Mermaid for all diagrams.
3. No secrets/credentials in the artifacts.
4. Generation metadata header at the top of each file.
5. Respect the dependency order between artifacts.
6. Write all artifacts in English.
